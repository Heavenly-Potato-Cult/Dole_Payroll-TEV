Turnover & Handover Guide

Document purpose: Internal technical reference for the incoming team taking over the DOLE RO9 Payroll System. Last reviewed: June 2026.

Read this first. This system is a Laravel 11 modular monolith with heavy HRIS dependency. Most operational data (employees, attendance, office orders) is pulled from an external HRIS API — not maintained locally as a source of truth.

What This System Does

  • Regular Payroll — Monthly payroll with full-month HRIS attendance pull, government deductions, loan enrollments, approval workflow (cutoff splits computed on the fly)
  • Special Payroll — Newly hired, salary differential, NOSI/NOSA, generic special
  • Allowances — Batch-based allowance processing with type CMS and per-employee standing allowances
  • TEV — Travel expense vouchers, office orders, cash advance/liquidation workflow
  • Government Remittances — GSIS, HDMF, PHIC, SSS, LBP, CARESS, MASS, Provident Fund, BTR exports
  • User Management — Super Admin creates officer accounts linked to employee records

Day-One Checklist for New Team

  1. Clone repo, run setup-xampp.bat or Docker setup per Local Setup
  2. Copy .env.example → .env; configure DB and HRIS variables (see Environment Variables)
  3. Confirm HRIS_USE_DUMMY=true for local dev unless you have official HRIS credentials
  4. Run migrations: php artisan migrate
  5. Seed super admin: php artisan db:seed --class=SuperAdminSeeder
  6. Login as admin@dole9.gov.ph / pass123 (change password immediately in production)
  7. Pull employees from HRIS: Employees → Sync from HRIS
  8. Create officer user accounts via User Management (Super Admin only)
  9. Review storage/logs/laravel.log after any HRIS pull — all sync operations are logged

HRIS Integration (Deep Dive)

Two Modes: Dummy vs Official

The system switches between dummy and official HRIS via a single flag: HRIS_USE_DUMMY in .env, read by config/services.php → services.hris.use_dummy.

AspectDummy API (HRIS_USE_DUMMY=true)Official HRIS (HRIS_USE_DUMMY=false)
Authentication Static bearer token via HRIS_API_KEY on every request POST login to HRIS_LOGIN_URL with HRIS_USERNAME, HRIS_PASSWORD, HRIS_DEVICE_NAME; receives bearer token
Base URL HRIS_API_URL HRIS_BASE_URL + dedicated HRIS_EMPLOYEES_URL
Employee response format { total: N, data: [...] } (flat array) { success: true, data: { current_page, last_page, data: [...] } } (paginated — all pages fetched automatically)
Fallback on failure Returns hardcoded mock employee if API empty Returns empty array or partial data — no mock fallback
Logging Standard info/warning logs Extensive logging — login URL, username, device name, token prefix, pagination progress, retry attempts (see below)

Dummy API (Development)

  • Deployed endpoint: https://dummy-api-bblh.onrender.com (also referenced: https://employee-api-dummy.onrender.com in older docs)
  • GitHub: employee-api-dummy
  • Auth: Authorization: Bearer {HRIS_API_KEY} — no login step
  • Local simulation: Node.js server in HRIS/ directory (npm start on port 3001) — see README.md

Official HRIS API (Production Target)

  • Portal: https://hris.dole9portal.org
  • Login: POST /api/login with username, password, device_name
  • Employees: GET /api/employees?page=N with bearer token
  • Credentials: Stored in .env — never commit real credentials to git
Official API logging: When HRIS_USE_DUMMY=false, HrisApiService::authenticate() logs the login URL, username, device name, HTTP status, and full response body to storage/logs/laravel.log. Token values are truncated in logs (first 20 chars only). Coordinate with HRIS IT on credential rotation — update .env and run php artisan config:clear.

HRIS Data Policy — Source of Truth

The payroll system does NOT push changes back to HRIS. HRIS is the authoritative source for employee master data. Any edits to personal information, position, or salary in the payroll UI are local overrides only and will be overwritten on the next HRIS sync (except fields explicitly preserved — see Employee Sync section).
  • Do not treat manual employee creation as the primary onboarding path — use HRIS pull
  • Do not expect HRIS to reflect payroll-side edits
  • Do coordinate with HRIS admin if employee IDs change — a re-pull is required
  • Do use local edits only for payroll-specific fields (deduction enrollments, exclusion flags, plantilla corrections)

Attendance Data Flow

  1. Payroll Officer creates/opens a batch (draft status)
  2. Clicks Pull Attendance or Pull & Compute
  3. AttendanceService@pullForBatch() calls HrisApiService@fetchAttendanceBulk()
  4. Results upserted into attendance_snapshots with source='hris_api'
  5. Employee matching tries multiple key formats: legacy EMP001, DB id, sequential index
  6. Missing employees logged as errors; no perfect-attendance fallback in bulk pull (unlike single-employee fetch)
  7. HR can manually correct snapshots (source='manual')

Employee Sync & ID Generation

Pull from HRIS — Process

Trigger: Employees index → Sync from HRIS button (roles: payroll_officer, hrmo, super_admin)

Route: POST /employees/pull-from-api → EmployeeController@pullFromApi()

Match & Upsert Strategy

FieldBehavior
hris_employee_id Primary match key. Stores raw HRIS employee_id (integer or string like EMP001). Used to find existing records including soft-deleted ones.
employee_no Locally generated on first sync only. Never overwritten on re-sync if already set. Used for login.
plantilla_item_no Preserved on update if already populated locally (manual corrections kept). Set from HRIS if currently NULL.
division_id Resolved by division_code from API. Auto-creates division if missing (see below).
Soft-deleted employees Restored automatically if they reappear in HRIS pull

Employee ID Generation (employee_no)

Employee numbers are not auto-incremented by the payroll database. They are derived from HRIS employee_id during sync.

Algorithm

Input:  HRIS employee_id (stored as hris_employee_id)

Step 1: Extract numeric portion
  "EMP001"  → "001" → "1"
  "123"     → "123"
  "EMP-456" → "456"

Step 2: Zero-pad to 4 digits
  "1"    → "0001"
  "12"   → "0012"
  "1234" → "1234"
  "12345"→ "12345"  (no truncation)

Step 3: Prefix
  → "EMP-" + padded = "EMP-0001"

Examples

HRIS employee_idLocal employee_no
1EMP-0001
2EMP-0002
123EMP-0123
EMP001EMP-0001
EMP-456EMP-0456
12345EMP-12345
HRIS coordination required: Employee matching relies on a stable integer/string employee_id from the HRIS API. The official HRIS does not currently populate an employee_no field on their end — payroll generates EMP-XXXX locally. If HRIS re-seeds or changes IDs, a full re-pull is needed and existing employee_no values are preserved (won't auto-update).

Database Fields

  • hris_employee_id — Original HRIS identifier (sync reference only)
  • employee_no — Local formatted ID (EMP-XXXX) used for login and display throughout the system

Division Auto-Creation

When pulling employees, divisions are resolved by division_code from the API payload:

  1. Look up local divisions table by code
  2. If not found and both division_code + division_name present → auto-create with is_active=true, description "Synced from HRIS"
  3. If division data missing entirely → employee skipped (logged as warning)

New divisions appear automatically in the division dropdown after sync — no manual seeding required.

Fields Synced from HRIS

On each pull, these fields are updated from API data: name, position, salary grade/step, basic salary, employment status, official station, appointment/promotion dates, government IDs (GSIS, Pag-IBIG, PhilHealth, TIN), division assignment, status (set to active).

Manual Employee Creation — Avoid

The create form at /employees/create does not generate employee_no or hris_employee_id. Manual entries won't participate correctly in HRIS attendance matching or SSO. Use HRIS sync as the primary path.

Office Order Pull — Employee Matching Caveat

Format mismatch bug: OfficeOrderController@pullFromApi() normalizes API employee_no (e.g. EMP-0001) to legacy format EMP001, but local records now use EMP-0001. Office orders may be skipped with "employee not found" until this normalization is updated to match the current employee_no format.

User Provisioning Flow (Officers)

  1. Super Admin goes to User Management (/users)
  2. Selects an existing employee record (must exist — pull from HRIS first)
  3. Assigns a primary role (e.g. payroll_officer, hrmo, accountant)
  4. Optionally assigns a secondary role (inactive by default)
  5. System creates User linked via users.employee_id with default password pass123
  6. Officer logs in with their employee_no + password
Login uses local employee_no only — not hris_employee_id. The HRIS integer/string ID is stored separately for sync reference.

Acting Officer — Role Activation

The user_role_assignments table tracks which user is the active acting officer for each role. Only one user can be active per role at a time.

  • Primary role: always active on creation
  • Secondary role: created inactive — Super Admin toggles via User Management
  • Activating a role for User A automatically deactivates that role for all other users
  • Spatie roles control access gates; UserRoleAssignment controls "who is acting right now" (used for signatory display)

Employee Self-Service Accounts

Employees without an officer role who log in (or arrive via future SSO) get the employee role and are redirected to My Payslip. They cannot access payroll management modules.

EmployeeAuthService handles employee login. Officers must be explicitly registered in User Management — position title keywords do NOT auto-grant officer roles.

Employee Login Auto-Provisioning

Problem solved: Employees could not login because the system required pre-existing User accounts, but only officers had accounts created via User Management. Regular employees had no way to access their payslips.

Why this was needed:

  • Originally, only officers (Payroll Officer, HRMO, Accountant, etc.) were registered in User Management
  • Regular employees had no User accounts in the system
  • The login flow required a User record to authenticate, blocking all employee access
  • HRIS SSO was scoped out, so employees needed a direct login path

How it works now:

  1. Employee enters their employee_no (e.g., EMP-0001) and password on the login page
  2. AuthController@handleEmployeeLogin() checks if a User account exists linked to that employee
  3. If no User exists: System auto-creates one with:
    • Name synced from employee record
    • Password hashed from the login attempt (first login sets their password)
    • employee role assigned automatically
    • Linked via users.employee_id
  4. If User exists: Password is verified against the stored hash
  5. Employee is logged in and redirected to My Payslip

Key implementation details:

  • Auto-provisioning only happens for employee ID logins (starts with "EMP")
  • Admin email logins are unaffected — they still require pre-created accounts
  • Auto-provisioned accounts get only the employee role — no officer access
  • Officers must still be explicitly registered by Super Admin via User Management

User Management Tabs (Employees vs Officers)

To support employee password management while keeping officer account management separate, User Management now has two tabs:

TabShowsActions
Officers Users with roles other than employee Create new officer accounts, edit roles, delete accounts
Employees Users with only the employee role Edit password only (no role changes, no deletion)

Why separate tabs?

  • Employees are auto-provisioned — no manual creation needed
  • Employees only need password management (forgot password, reset by admin)
  • Officers need full account management (roles, assignments, activation)
  • Prevents accidental deletion of employee accounts (they're auto-created on login anyway)

Employee password reset flow:

  1. Super Admin goes to User Management → Employees tab
  2. Clicks Edit on an employee
  3. Simplified form shows only password fields (no role assignment)
  4. Enters new password and confirmation
  5. Employee can login with new password on next attempt
Security note: Employee accounts are created with the password they provide on first login. Super Admin should encourage employees to use strong passwords and can reset them via the Employees tab if needed.

How Access Is Enforced Today

The system uses three overlapping mechanisms — this is intentional legacy, not ideal architecture:

  1. Spatie Laravel Permission — Roles stored in roles / model_has_roles tables; route middleware role:payroll_officer|hrmo|...
  2. Blade @role() directives — Hardcoded role strings in sidebar layouts (app.blade.php, tev.blade.php) control which nav items render
  3. Inline controller checks — authorizeRole() methods and direct hasRole() calls in controllers

Central role group constants live in app/SharedKernel/Services/RoleService.php (PAYROLL_ROLES, TEV_ROLES, etc.).

Why Officer Role CMS Was Not Implemented

Recommendation to incoming team: Do NOT attempt a dynamic role/module CMS without a full architecture redesign.

A previous recommendation suggested building a CMS for officer roles (like the existing Deduction Type CMS). After implementation attempts, this was determined to be not feasible in the current codebase without a complete architectural overhaul:

  • 8+ distinct roles (Payroll Officer, HRMO, Accountant, ARD, Cashier, Budget Officer, Chief Admin Officer, Super Admin) — each with different module visibility, action permissions, and workflow steps
  • Sidebar rendering is hardcoded with @role('payroll_officer|hrmo|...') blocks in Blade templates — not driven by a permission registry
  • Workflow actions (submit, certify, approve, lock) are embedded in controllers with inline role checks, not policy-driven
  • Dual role system (primary + secondary with activation toggle) adds complexity beyond simple admin/user binary
  • Previous attempts to refactor caused cascading bugs — especially the not stableversion branch with enum-based permissions (see Known Issues G-07)

What Would Be Needed (Future Architecture)

For a proper dynamic role system, plan these layers before coding:

  1. Permission registry — Database-driven or enum-backed list of granular permissions (view_payroll, compute_payroll, certify_payroll, etc.)
  2. Role-permission matrix CMS — Admin UI to assign permissions to roles without code changes
  3. Dynamic menu builder — Sidebar generated from user's permission set, not hardcoded Blade blocks
  4. Policy layer — Replace inline authorizeRole() with Laravel Policies on all models
  5. Middleware — Reusable permission-check middleware instead of per-route role strings
  6. Migration strategy — Map existing 8 roles to new permission sets; test every workflow stage

A simpler employee | admin binary would work for traditional systems but does NOT fit DOLE RO9's multi-officer approval chain. Attempting to simplify without redesign will break TEV and payroll workflows.

What Works Today (Safe CMS Patterns)

  • Deduction Type CMS — Fully functional; safe to extend
  • Allowance Type CMS — Same pattern as deductions
  • Signatory Management — Assigns document signers by role
  • User Management — Super Admin assigns Spatie roles to users (not a CMS for role definitions themselves)

Branch Note: not stableversion

A remote branch attempted type-safe enum permissions (@can(Permission::PAYROLL_VIEW)). It causes dashboard layout duplication bugs when merged without refactoring Blade wrappers. Do not merge without a dedicated UI refactor pass.

DOLE Payroll System

DOLE Regional Office 9 Payroll Management System

A Laravel-based payroll system for DOLE RO9 that handles regular payroll processing, special payroll types (newly hired, salary differential, NOSI/NOSA), travel expense vouchers (TEV), office orders, and government remittance reports.

Who Uses It

The system serves multiple roles with specific permissions:

  • payroll_officer — Creates and computes payroll batches, manages employees
  • hrmo — Manages employees, office orders, TEV requests, files liquidations
  • accountant — Certifies payroll funds, reviews TEV requests
  • ard / chief_admin_officer — Approves payroll and TEV requests
  • cashier — Releases payroll, handles TEV cash advances and liquidations
  • budget_officer — Monitors TEV submissions for reference

Main Features

  • Regular Payroll — Monthly payroll with full workflow: draft → compute → submit → certify → approve → lock (cutoff splits computed on the fly from daily_logs)
  • Special Payroll — Newly hired pro-rated payroll, salary differential, NOSI/NOSA
  • TEV Management — Travel expense vouchers with itinerary, approval workflow, cash advance tracking, and liquidation
  • Office Orders — Authorization documents for official travel
  • Employee Management — Employee records with deduction enrollments, promotion history
  • Government Remittances — GSIS, HDMF/Pag-IBIG, PHIC, SSS, and various loan remittances (LBP, CARESS, MASS, Provident Fund, BTR)
  • Reports — Payroll register, payslips, TEV reports, remittance exports
  • Authentication — Role-based access control with admin login and employee registration
  • Deduction Type CMS — Full content management system for deduction types
  • Signatory Management — Document signatory assignment and management

Local Setup

The project supports two setup methods: XAMPP (recommended for Windows) and Docker (edge case for PCs without PHP).

XAMPP Setup (Recommended)

Note: An automated setup script is available: setup-xampp.bat
  1. Install XAMPP from apachefriends.org
  2. Start Apache and MySQL services in XAMPP Control Panel
  3. Clone the repository
  4. Run setup-xampp.bat (this auto-detects XAMPP, creates database, runs migrations, imports data)
  5. Or manually:
    • Copy .env.example to .env
    • Run php artisan key:generate
    • Configure database in .env (XAMPP defaults: DB_HOST=127.0.0.1, DB_USERNAME=root, DB_PASSWORD=)
    • Run php artisan migrate
    • Run php artisan db:seed
  6. Start the server: php artisan serve
  7. Access at http://localhost:8000

Docker Setup (Edge Case)

Warning: Docker is provided as an edge case for PCs that cannot install PHP locally. Use XAMPP setup if possible.
  1. Install Docker Desktop and ensure it's running
  2. Clone the repository
  3. Run .\initial_start.bat (Windows) or docker compose up
  4. Access at http://localhost:8000
  5. Adminer available at http://localhost:8080 for database management

Common Pitfalls

  • XAMPP Path Detection: The setup script looks for XAMPP in common paths (C:\xampp, D:\xampp, C:\Program Files\xampp). If installed elsewhere, manual setup is required.
  • Database Creation: The dole_payroll database must exist before running migrations. The setup script handles this automatically.
  • .env Configuration: Ensure SESSION_DRIVER=database, CACHE_STORE=database, and QUEUE_CONNECTION=database are set for proper operation.

Key Modules

Regular Payroll

Flow:

  1. Payroll Officer creates batch (year, month, period_start, period_end) — single batch covers full month
  2. System generates PayrollBatch in draft status
  3. Payroll Officer clicks "Compute" → PayrollComputationService processes all active employees:
    • Calculates gross income (basic + PERA + RATA, monthly with on-the-fly cutoff breakdown)
    • Calculates attendance deductions (LWOP, tardiness using Table IV)
    • Calculates government deductions (Pag-IBIG, PhilHealth, GSIS, WHT using annualized method)
    • Applies enrolled loan deductions
    • Computes net pay
  4. Batch status changes to computed
  5. Payroll Officer submits → pending_accountant
  6. Accountant certifies funds → pending_rd
  7. RD/ARD approves → released
  8. Cashier locks after disbursement → locked
  9. Force edit override allows reverting from locked to released (requires remarks)

Payslip Generation

Enhanced Features:

  • Payslips are generated from monthly payroll batches with on-the-fly cutoff breakdown (1st: days 1-15, 2nd: days 16-end)
  • "My Payslip" feature allows employees to view their payslips
  • Signatory information is included on payslips for proper authorization
  • Payslip views have been enhanced with better formatting and layout
  • Redesigned My Payslip Page: New UI with filtering options by month/year, improved responsive design
  • Employee-Specific Access: Employees can only access their own payslips through proper session management

Special Payroll

Types: Newly Hired (pro-rated), Salary Differential, NOSI (Non-Optimization of Salary Increase), NOSA (Non-Optimization of Salary Adjustment)

Flow:

  1. HRMO creates special payroll batch with employee, effectivity dates, salary amounts
  2. Service computes pro-rated or differential amount based on working days
  3. Batch created in draft status
  4. Accountant approves → approved
  5. RD/ARD releases → released

TEV (Travel Expense Voucher)

Tracks: Cash Advance (requires liquidation) or Reimbursement

Flow:

  1. HRMO creates Office Order (authorization for travel)
  2. HRMO creates TEV linked to approved Office Order with itinerary lines
  3. TEV auto-submits on creation (no draft state — HRMO files directly)
  4. Accountant certifies → accountant_certified
  5. RD/ARD approves → rd_approved
  6. Cashier releases:
    • Cash Advance: Records cash advance amount, status → cashier_released
    • Reimbursement: Status → reimbursed
  7. After travel, HRMO certifies travel completion (optional Annex A expenses)
  8. For Cash Advance: Employee or HRMO files liquidation with actual amount spent
  9. System calculates balance due (positive = refund, negative = additional payment)
  10. Cashier approves liquidation → liquidated

Role-Based TEV Dashboard

Enhanced Access Control:

  • Employee-Specific Views: Employees see only their own TEV requests and pending actions
  • Officer Dashboard: Officers see TEV requests requiring their approval based on role
  • Role-Based Routing: Automatic routing to appropriate dashboard based on user role after login
  • Dedicated TEV Layout: Separate TEV layout (`layouts/tev.blade.php`) for better UI separation

Office Orders

Purpose: Authorization documents for official travel, required before creating TEV requests

Flow:

  1. HRMO creates Office Order manually OR pulls from Employee API
  2. Office Order created in draft status (manual) or approved status (pulled from API)
  3. RD/ARD approves draft Office Orders → approved
  4. HRMO creates TEV linked to approved Office Order
  5. Office Orders can be cancelled if no TEV requests are linked

Pull Office Orders from API

Feature: HRMO can pull approved Office Orders directly from the dummy HRIS Employee API to sync with the local system

Access: Available to users with roles: payroll_officer, hrmo, super_admin

Process:

  • HRMO clicks "Pull Office Orders" button on Office Orders index page
  • System calls HrisApiService@fetchOfficeOrders() to fetch 164 approved orders from dummy HRIS Employee API
  • API endpoint: GET /office-orders (returns { total: 164, data: [...] })
  • System matches employees by employee_no (normalizes format from "EMP-0001" to "EMP001")
  • Creates new Office Order records or updates existing ones based on office_order_no
  • All pulled orders are set to approved status with approved_at timestamp from API
  • Progress bar shows sync status with real-time feedback
  • System logs sync statistics: synced count, updated count, skipped count (employee not found)
  • Returns JSON response with success/error message for AJAX handling

Error Handling:

  • Orders are skipped if matching employee is not found in local system
  • 60-second timeout for API request
  • JSON parsing errors handled gracefully with user-friendly error messages
  • All sync operations logged for audit trail

System Overview

The DOLE Payroll System is a comprehensive payroll and travel expense management system for Department of Labor and Employment Regional Office IX. The system handles monthly payroll processing with on-the-fly cutoff breakdown, government remittances, travel expense vouchers (TEV), and office orders with role-based access control.

Business Domains

The system is organized into two main business domains:

  • Payroll Module: Regular payroll processing, special payroll, government remittances, payslip generation, deduction management
  • TEV Module: Travel expense vouchers, office orders, cash advances, liquidation, and travel approvals

System Architecture

The system follows a modular Laravel 11 architecture with two separate modules:

  • Modules/Payroll/ - Payroll-specific functionality
  • Modules/Tev/ - TEV-specific functionality
  • App/SharedKernel/ - Shared models (Employee, User, DeductionType)

Why Modular Monolith Instead of Solid Monolith?

Architecture Evolution: The system was initially designed as a solid monolith but was refactored to a modular monolith as the team discovered that Payroll and TEV are fundamentally different business domains with distinct workflows, data models, and lifecycle requirements.

Key Reasons for Modular Architecture:

  • Business Domain Separation: Payroll (monthly processing with on-the-fly cutoff breakdown, government remittances, tax computation) and TEV (travel authorization, cash advances, liquidation) have completely different business logic, approval chains, and data structures. Keeping them in separate modules prevents code coupling and makes each domain easier to understand and maintain.
  • Future Scalability: As the system evolves, each module can be enhanced, refactored, or even extracted independently without affecting the other. This allows for future scenarios where one module might need significant changes while the other remains stable.
  • Shared Approval Chain: Despite being separate domains, Payroll and TEV share the same officer approval chain (HRMO, Accountant, ARD, Chief Admin Officer, Cashier). The modular architecture allows these shared roles to be defined once in App\SharedKernel\Services\RoleService.php while keeping the business logic separate.
  • Clear Boundaries: The modular structure enforces clear boundaries between domains. Payroll-specific code lives in Modules/Payroll/, TEV-specific code lives in Modules/Tev/, and truly shared entities (Employee, User, DeductionType) live in App/SharedKernel/.

Shared Officers Across Modules:

The following officer roles participate in both Payroll and TEV approval workflows:

RolePayroll ResponsibilitiesTEV Responsibilities
hrmo Employee records, office orders, TEV creation Create TEV requests, file liquidations, manage office orders
accountant Certify payroll funds, review TEV requests Certify TEV requests, review liquidations

budget_officer TEV monitoring, office order visibility Review TEV budget allocations, monitor submissions

Implementation:

The modular architecture is implemented using the nwidart/laravel-modules package (v12.0), which provides a structured way to create and manage Laravel modules. Each module has its own routes, controllers, models, views, and service providers, while maintaining the ability to share common code through the SharedKernel.

Design Trade-off: While microservices would provide even stronger separation, the modular monolith approach was chosen because (1) the shared approval chain and database make microservices over-engineered for current needs, (2) deployment complexity would increase significantly, and (3) the team can extract modules to microservices in the future if needed without major rewrites.

Integration Points

  • HRIS API Integration: Attendance data is fetched from external HRIS API via HrisApiService@fetchAttendanceBulk() and stored in attendance_snapshots table
  • Database: MySQL database with Laravel Eloquent ORM
  • Authentication: Laravel Sanctum for API authentication, session-based web authentication
  • Authorization: Spatie Laravel Permission for role-based access control

Business Processes

Regular Payroll Workflow

The regular payroll process follows a multi-stage workflow:

  1. Payroll Batch Creation: Payroll Officer creates monthly batch (period_start to period_end covering full month) — status: draft
  2. Attendance Data Pull: HRIS API → attendance_snapshots via AttendanceService@pullForBatch()
  3. Payroll Computation: Calculates gross, attendance deductions (Table IV), government deductions, loans, net pay — status: computed
  4. Submission: Payroll Officer submits → pending_accountant
  5. Accountant Certification: Certifies funds → pending_rd
  6. RD/ARD Approval: Approves and releases → released
  7. Cashier Lock: After disbursement → locked
  8. Force Edit: Payroll Officer can revert locked → released (requires remarks)
  9. Payslip Generation: After release; employees via My Payslip

TEV Workflow

Travel Expense Voucher process:

  1. TEV Creation: HRMO creates TEV request on behalf of employee with travel details, itinerary, and estimated expenses
  2. Office Order Generation: System generates office order authorizing the travel
  3. Budget Officer Review: Budget Officer reviews and approves the budget allocation
  4. ARD Approval: Assistant Regional Director approves the TEV
  5. Cash Advance Disbursement: Cashier processes cash advance (if applicable)
  6. Travel Execution: Employee undertakes travel
  7. Liquidation Filing: Employee files liquidation with actual expenses and receipts
  8. Accountant Review: Accountant reviews liquidation and computes refund or additional disbursement
  9. Cashier Final Processing: Cashier processes final payment or refund

Government Remittances

Government remittance exports are generated for:

  • GSIS: Summary and detailed remittance reports with loan breakdowns
  • HDMF/Pag-IBIG: P1, P2, MPL, Calamity, Housing loan remittances
  • PHIC: PhilHealth contributions CSV export
  • SSS: SSS voluntary contributions CSV export
  • LBP Loans: Landbank loan remittance export
  • CARESS: Union dues and mortuary aid remittances
  • MASS: MASS membership remittance
  • Provident Fund: DOLE Provident Fund contribution remittance
  • BTR Refund: BTR refund remittance export

The active codebase relies on hardcoded Spatie role strings in three places:

  1. Route middleware: role:payroll_officer|hrmo|...
  2. Blade sidebar: @role('payroll_officer|hrmo|...') in layout templates
  3. Controller inline checks: $this->authorizeRole([...])

Super Admin Access

Super Admin (super_admin role) has access to User Management and can view most modules. Individual Blade blocks grant super_admin alongside officer roles. There is no global Gate::before bypass in the current AppServiceProvider — access is per-template.

Dual Role System

Users can hold a primary role and optional secondary role via Spatie. The user_role_assignments table tracks which assignment is the active "acting officer" for signatory purposes. See User Accounts.

Do not merge not stableversion branch without refactoring Blade layout wrappers. The enum-based permission system causes dashboard card duplication for multi-role accounts.

Data Flows

Attendance Data Flow

Attendance data flows through the system as follows:

  1. HRIS API: External HRIS system stores employee attendance records
  2. AttendanceService@pullForBatch(): System calls HRIS API to fetch attendance for all active employees for a payroll period
  3. Attendance Snapshots: Data is upserted into attendance_snapshots table with source='hris_api'
  4. Manual Corrections: HR can manually correct attendance snapshots if needed (source='manual')
  5. PayrollComputationService: Reads from attendance_snapshots to compute attendance deductions
  6. Payroll Entries: Attendance deductions are stored in payroll entries

Payroll Computation Data Flow

  1. Employee Data: Employee records with salary, deductions enrollments, and other attributes
  2. Attendance Data: From attendance_snapshots (LWOP days, late minutes, undertime minutes)
  3. Deduction Enrollments: Employee loan enrollments with deduction types and amounts
  4. PayrollComputationService@computeEntry(): Processes individual employee payroll
    • Computes gross income (basic + PERA + RATA)
    • Computes attendance deductions via AttendanceService
    • Computes government deductions via DeductionService
    • Applies loan deductions via DeductionService
    • Computes net pay
  5. Payroll Entries: Results stored in payroll_entries table
  6. Payroll Deductions: Individual deductions stored in payroll_deductions table

Authorization Flow

  1. User Login: User authenticates via Laravel Sanctum or session
  2. Role Assignment: User has main role and optional sub role via user_role_assignments table
  3. Permission Check: Spatie Laravel Permission checks role-based permissions
  4. Inline Authorization: Controllers perform additional inline role checks via authorizeRole() method
  5. Access Granted/Denied: User is granted access or redirected based on role

Quirks & Decisions

Database Relationship Desyncs

Critical Development Caveat: When executing database seed executions via php artisan db:seed --class=RolePermissionSeeder, all existing authorization maps in the polymorph tables are systematically flushed.

Because employee profiles link authentication via employee_id rows rather than standard user string schemas, running a local seeder will drop permissions and hide components globally. To restore dashboard access without manual string mapping scripts, immediately inject the primary key directly into your terminal runtime via Artisan Tinker:

// Instantly binds your administrator credentials back to the security loop
php artisan tinker
>> \App\Models\User::find(1)->syncRoles('super_admin');
>> app()[\Spatie\Permission\PermissionRegistrar::class]->forgetCachedPermissions();

TEV Auto-Submission

TEV requests are auto-submitted on creation. There is no draft state for TEVs. This is intentional because HRMO files TEVs on behalf of employees — the draft state was redundant. The submit() method exists but aborts with a 410 error if called.

Payroll Force Edit Override

Locked payroll batches can be force-edited back to released status by the Payroll Officer. This requires a mandatory remarks field (10-1000 characters) and is logged in the audit trail. This is a safety valve for post-disbursement corrections.

Attribute Aliases in Employee Model

The Employee model has attribute accessors that alias column names to match what services expect:

  • basic_monthly_salary → basic_salary column
  • pera_amount → pera column

This allows services to use consistent naming while the database uses shorter column names.

SpecialPayrollBatch Single Table

All special payroll types (newly_hired, salary_differential, nosi, nosa) share one table with a type column. This simplifies the schema but means some columns are only relevant for certain types (e.g., pro_rated_days only for newly_hired).

Table IV Minute Conversion

Tardiness and undertime minutes are converted to decimal days using a lookup table (DOLE Table IV), not a simple division. The TableIVConverter trait handles this. For example, 15 minutes = 0.031 days (from table), not 0.03125 computed.

Working Day Denominator

All salary computations use a fixed 22 working days per month denominator, regardless of actual calendar days. This is per DOLE RO9 payroll rules and is hardcoded in multiple services.

Net Pay Verification

The /payroll/{payroll}/verify endpoint shows net pay for the monthly batch with on-the-fly cutoff breakdown, flags employees below ₱5,000 threshold, and identifies LBP loan deductions. This is for cashier verification before disbursement.
